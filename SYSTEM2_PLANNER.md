# System-2 Local Planner

This phase adds an **experimental typed local planner**. `SYSTEM2_PLANNER_REPORT.md`
contains the original phase qualification results. The focused next-action follow-up is recorded in `SYSTEM2_FOCUSED_REPORT.md`. The feature defaults off. Automatic
Apple Voice Agent fallback is gated off independently of Laya; Laya neither
approves nor supplies planner tools or arguments.

## Execution boundary

`PlannerRouter` preserves deterministic direct requests. `VoiceAgentCoordinator.runPlanner`
uses the existing action ledger, `ActionExecutor`, `ToolRegistry`, confirmation
challenges, receipts and guarded Undo. There is no second OS executor. The model
suggests registered calls; `PlannerValidator` checks the whole batch before the
first effect and context again before each subsequent send. Native preparation
freezes approved targets and registry risk always determines confirmation.

The helper uses the pinned native MLX `Qwen35ToolCallParser` for XML and Hermes JSON inside `<tool_call>` framing. Bare JSON and prose recovery are forbidden. Each production turn contains exactly one function call: a registry tool or a no-effect `decision.finish`, `decision.askUser`, or `decision.abstain`.
It does not infer actions from prose. Native assistant/function calls and tool-response roles carry validated argument arrays and compact receipts. A helper-typed EOS assistant stop discards its answer text before IPC; it does not verify goal completion. Truncated or malformed tool envelopes remain errors. Unknown IDs/fields, invalid types/enums,
missing slots, unsafe paths, cyclic or missing dependencies and batches over
8 steps are rejected. Sequential Qwen calls acquire host dependencies; readiness
steps require verified receipts. A browser call to localhost must exactly match
a saved service and follow a genuine verified `service.wait`/`service.status`
receipt or a validated wait dependency. A process-start receipt is not readiness.

The initiating request freezes a host-owned `GoalEnvelope`. Domains, explicit projects, requested workflows/sites and search subject cannot be enlarged by receipts or file text. Each turn exposes at most 12 functions, usually 4–8 including three decision functions. Stable project/search/file/workflow/service/app handles are resolved by the host; native paths and executable arguments are not regenerated by Qwen. Only relevant compact receipts enter the prompt. Satisfied goals expose decision functions only.

The loop executes the next useful step, observes a compact typed receipt and
calls the resident model again. Limits are 8 initial/batch steps, 16 executed
steps and 4 failure replans, with at most 17 generation turns per approved budget.
Only failed read operations permit bounded retry. Aliases and equivalent editor
IDs cannot repeat already-delivered effects. Continuation requires an explicit
Settings click and retains the prior ledger. Every consequential action still
requires the existing frozen single-use confirmation.

Cancel stops generation, unsent steps and owned wait tasks. Completed effects and
valid existing Undo remain. Cancel does not kill a successfully started workflow:
that is a completed real effect. `workflow.stop`, with confirmation, stops it.
Application termination kills LocalFlow-owned workflow groups and the model helper. A native lifetime guard reserves each process group before its workflow starts, acknowledges readiness, ignores graceful TERM and kills its group on parent-pipe EOF. This also covers parent loss during shutdown. Workflows must stay in their foreground process group; detached/self-daemonizing descendants are not qualified.

## Resident runtime and setup

Qwen3.5-4B 4-bit weights are the only planner checkpoint. The bundled
`model-manifest.json` pins repository revisions, byte lengths and SHA256 for every
asset. Settings Download is explicit, reports progress, hashes staged files and
publishes atomically; Remove touches only this planner installation. Model load
is explicit and verifies model and native runtime hashes first.

The production path is a persistent **Swift MLX helper**, using local stdin/stdout
JSON, owned by LocalFlow. It loads local files only, receives no images, runs no
HTTP server, and never automatically writes conversation content. A serial worker
bounds IPC and generation deadlines. Cancellation terminates the owned child,
escalates if necessary and requires explicit reload. Helper failures do not crash
LocalFlow. LocalFlow's root package retains no external dependencies.

The helper retains a cache only for the host system instructions and generated
registry schemas, ending before the first template-owned user boundary. Every
request uses an independent cache copy for its goal, saved context and receipts;
that suffix is discarded. Reasoning is discarded by actual Qwen special token IDs inside the helper before collecting reply fragments or sending IPC. Quoted look-alike tags cannot release calls or reasoning. Non-envelope assistant text is discarded; malformed and truncated envelopes are rejected.
Settings Prepare/Load primes the registry prefix before reporting warm/resident.

For this local development checkout, run `Scripts/prepare-planner.sh` to build
and install the pinned native helper, freeze its artifact hashes, then rebuild
the app. After benchmarking, explicitly import the single staged candidate through
`swift run localflow-planner-setup --install-candidate "$PWD/.build/system2/candidate"`.
This uses the real PlannerModelManager's checksum verification and atomic import,
then prepares and unloads a local health probe. It changes no project memory or
feature toggle. `swift run localflow-planner-setup --health` checks the existing installation without importing another model. This is an internal runtime build, not an application release package.
The installed Xcode lacks its optional Metal compiler. The setup script uses the
hash-verified official Apple `mlx-metal` shader artifact matching the Swift MLX
core revision; the provenance is in `Evaluation/System2/native-metal-provenance.json`.
No optional Xcode component is installed by this script. The former duplicate candidate staging directory and Python comparator environment were removed after their completed evaluation; the installed checkpoint is the sole active Qwen copy.

Settings → Agent / Mac Control → System-2 Planner offers Download, Prepare/Load,
Unload, Cancel, Remove and Experimental Planner. Debug builds expose typed goals
and numeric generation metrics. The island reuses current action/progress,
confirmation, Cancel and terminal states. No chain of thought appears in UI.

## Explicit project memory

Projects are optional v1 JSON fields, preserving old memory files and their
atomic publication, size bounds and stale-write protections. Add records through
Settings' existing operational JSON editor. There is no automatic Mac scan,
silent path learning, auto-created workflow or production project fixture.

Example **shape** (the executable/arguments must be supplied and approved by the
user; do not copy this placeholder into operational memory):

```json
{
  "name": "MyProject",
  "aliases": ["my project"],
  "folder": "/absolute/project/folder",
  "preferredEditor": "com.microsoft.VSCode",
  "websiteURL": "https://example.com/my-project",
  "serviceURL": "http://127.0.0.1:3000",
  "workflows": [],
  "importantFiles": {"agent": "Sources/Agent.swift"}
}
```

An approved workflow contains `name`, absolute `executable`, an `arguments` array,
absolute project-contained `workingDirectory` and `approvedByUser: true`.
`workflow.run` receives only project and saved workflow names, never executable
or shell text. Shell interpreters and launcher indirection are unsupported.
Workflows spawn directly into owned process groups with fixed environment,
closed stdin, bounded 8 KiB output capture, cancellation, escalation and reaping.
LocalFlow never adopts a model-supplied PID. Frozen workflow configuration cannot
change under a confirmation grant.

Project resolution requires one explicit saved name/alias. Searches are bounded
to that project (5,000 entries / 8 MB text / 20 results), skip symlinks and common
build/vendor directories, and return relative files/lines. Files must stay inside
the canonical saved folder and cannot be executable launch files. File/editor
and Finder requests remain unverified without readback; they manufacture no Undo.
VS Code line navigation is requested through its existing launch arguments and
is explicitly unverified. Symbol reveal currently returns text matches.

Services use only an explicitly saved credential-free loopback HTTP(S) URL.
Readiness uses a cancellable bounded HEAD request, ephemeral URLSession and no
redirect following. It verifies HTTP response readiness, not application health.

## Validation and rerunning evidence

`Evaluation/System2/scenarios.json` freezes 108 typed scenarios, with authored
first-tool/argument gold slots. `PlannerBenchmarkTests` separates deterministic
routing/validator/mock execution evidence from opt-in real model evidence.
`benchmark_runtime.py` compares the same registry-derived wire requests, four
workloads and both thinking modes in one resident process per runtime. The Python
MLX environment is an evaluation comparator, not an app inference requirement.
`run_model_evaluation.py` runs these sequentially to avoid simultaneous models.

Model-backed tests require explicit `LOCALFLOW_PLANNER_MODEL` and
`LOCALFLOW_PLANNER_EXECUTABLE` paths plus the relevant output path. Read-only
iterative examples have a test boundary that admits repository queries only;
they write no real operational memory and launch no editor/browser/workflow.
Evidence labels distinguish those real reads from mocked effects and initial-plan
metrics. The 24 iterative model missions additionally measure required-effect coverage, using explicitly simulated receipts and benchmark-only confirmation grants. Neither passing structural validation nor a model assistant stop proves
that a whole development mission completed.

No screenshots, Screen Recording request, vision adapter, coordinate action,
OmniParser or ShowUI integration exists in this phase. `PlannerContext` is a
versioned text boundary suitable for a separate future observation extension.
